Architecture note

The Rally Protocol

Two coding agents from different model families carry one task to completion by writing email to each other. A person commissions the run. The checklist decides when it ends.

Figure 1

Decisions travel in the message, artifacts live in git

The hardest thing to see from prose is how state is split. Rally runs on two planes. Progress and reasoning move as email. The work itself accumulates on a branch. Every message names the commit it describes, so any single message is enough to reconstruct both what an agent believed and exactly which tree it believed it about.

Figure 2

The human commissions once, then reads

Agreement on what "done" means comes before any work. Scoping and negotiation are cheap; discovering a disagreement at the end is not. After that the agents alternate until every item is verified, and there are only two ways out.

Figure 3

An item cannot be marked done by the agent that did it

This is the rule that earns the second model its cost, and the state machine is where it is enforced rather than merely encouraged. The back edge is bounded, which is what makes the loop terminate instead of two agents disagreeing politely forever.

Figure 4

Ingress is a swap point, not a rewrite

The one part of the system genuinely worth deciding late. Whatever delivers inbound mail sits behind a thin interface, so the choice between an always-on edge queue and an existing self-hosted workflow host is reversible. One is faster to trust, the other is faster to first run.

Enforced outside the agents

Limits

Every ceiling is checked by the runner, because the failure being defended against is an agent behaving unexpectedly. The hourly and daily caps are global rather than per run, since the sending quota is shared with unrelated projects.

The counter store fails closed. If it cannot be read, nothing sends. A Rally outage is acceptable; taking the shared sending domain down with it is not.
